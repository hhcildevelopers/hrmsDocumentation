# 8. Common Errors & Solutions

[← Handbook](README.md)

Use this page when a screen shows an error, a button is unavailable, or a punch is not confirmed. The exact words can vary by language and portal. On the Field Portal, **Details for supervisor** may show a technical code; employees normally need the plain-language message instead. A red/amber message is not proof that attendance was recorded. Check **Punches** for the final server result.

**Before trying again:** check the selected company, the correct account, phone internet, and the date/time of the duty. Tap **Refresh** once. If a punch may already have been sent, check its result before attempting another. Do **not** clear browser storage or uninstall the Field Portal when punches are waiting to sync: that can erase the only local copy. Never send a password, one-time password, full Aadhaar/PAN number, or bank account number to support.

## Phone registration and saved punches

### “This browser was used for attendance before”

This means the Field Portal tried to register a browser ID that is already in the attendance-device history. It often happens when a Chrome profile used for **employee A** is later used for **employee B**, or when an old profile is reused after a phone change. It is **not an internet problem**. The current device policy keeps each browser ID unique, so repeated Refresh will not register that same ID. You can still read server-stored duties and earlier attendance, but this browser cannot punch until a valid attendance device is enrolled.

1. Open **Punches** and check whether this browser has any waiting or uncertain punches. If it does, **do not clear site data**. Tell your supervisor so the evidence can be handled.
2. For another employee on the same computer, use that employee's **own persistent Chrome profile** (not a shared profile or temporary Incognito window), or use their own phone. Sign in there and follow **Use this phone for attendance** if prompted.
3. If this is the employee's usual device and the warning remains, contact HR/Admin. Give the employee code, selected company, approximate time and the exact message, but not any password or browser ID.

**HR/Admin:** Verify the account-to-employee link and review the employee's attendance-device history. A phone-change **usage reset only changes the allowance**; it does not make a previously registered browser ID reusable. If another profile/phone is not practical, escalate to technical support rather than deleting device history or changing the database by hand. Resolve any missing punches with the normal attendance-review/exception process.

| What you see | Meaning and likely cause | What you should do | When to ask for help; HR/Admin action |
| --- | --- | --- | --- |
| **Use this phone for attendance** | Another device is selected, or this one has not been enrolled. Reading server history is still allowed. | First sync any saved punches on the old phone if possible. Then tap **Use this phone** on the new device. The old phone's unsynced punches do not transfer. | If the old phone is unavailable and evidence is missing, tell your supervisor. | **Phone change already being processed / Retry** | Two enrollment/switch requests collided or the database was briefly busy. | Wait a moment and tap **Refresh** once. Check whether this phone now says it is ready. Avoid repeated rapid taps. | If it persists, HR checks the device history and asks technical support to inspect a stuck operation. |
| **Could not check this phone** | The device-status request failed for a network, session, or server reason. The message does not mean the phone is approved. | Check internet, sign in again if prompted, then tap **Refresh**. Do not punch until the phone status is known. | If internet works but the error continues, HR/Admin checks backend availability, account link and request logs; report the time and displayed message. |

A saved local punch alone is not paid attendance. |

Do not assume it is confirmed. | Attendance reviewer checks shift, site policy, location/time evidence and prior session, then records a decision or justified exception. |

## Duties, punch windows and GPS

| What you see | Meaning and likely cause | What you should do | When to ask for help; HR/Admin action |
| --- | --- | --- | --- |
| **No duty / Wrong site or shift** | No active assignment applies, today is not a selected working day, or a transfer changed the assignment. | Refresh **Home** and **Shifts**; check the local duty date, including overnight shifts. Do not punch at an unassigned site. | HR checks the current assignment, weekdays, common shift, site policy and pending transfer; corrects with the normal assignment/transfer workflow. |
| **Transfer pending / Destination not punchable** | The employee still has an open session at the original site. | Finish that site's punch-out if possible. Do not start duty at the destination in the system yet. | HR/reviewer checks the old session; a verified exception punch-out can close it and activate the transfer. Preserve old-site history. |
| **Punch in opens at … / Outside shift window** | The server's allowed punch window has not opened or has closed. Changing the phone clock will not help. | Wait until it opens. For a closed or past duty, contact the supervisor instead of trying GPS again. | HR confirms assignment and local site timezone; an authorized reviewer considers a documented correction/exception. Do not change old shifts to hide the issue. |
| **Already punched / Another active duty / Conflict** | A punch or open session already exists, or another action changed the duty while you were using it. | Open **Punches**, refresh once, and check the confirmed result. Do not repeatedly submit. | Reviewer inspects the actual session and event reference; resolves any missing punch through the approved process. |
| **Location permission denied / Location unavailable** | Browser/phone location access is blocked, GPS is off, or the phone cannot get a fix. | Enable location in phone settings, allow this site in browser permissions, move to an open area and try **Check my location**. | If the device cannot provide location during duty, notify the supervisor promptly. HR follows the documented attendance exception policy. |
| **Location requires a secure connection** | Phone/browser geolocation generally requires HTTPS (localhost is a special development exception). | Use the approved HTTPS Field Portal address, not an `http://` LAN address. | Admin/IT supplies a secure deployment or test URL; do not ask employees to bypass browser security. |
| **Location accuracy too low / Stale location** | The fix is too uncertain or old for this site's rule. For example, 138 m accuracy fails a 50 m requirement. | Stand safely in an open area at the site and request a **fresh** reading, then punch. Do not rely on the earlier map preview. | If repeated at the real duty point, HR/IT checks the site accuracy limit and tests with a real handset; do not falsify coordinates. |
| **Outside site boundary** | The phone's position plus its accuracy cannot be confirmed within the configured circle. | Move farther inside the permitted site area and retry with a fresh reading. | If the pin/radius is wrong, an authorized admin verifies the gate/post on site and creates a new geofence policy version. |
| **You are late / Reason required** | Your internal-employee punch-in is after the company policy's grace period. A reason is needed before the punch can be accepted. | Enter a truthful reason of at least 10 characters and submit the same duty punch. Do not change your phone clock. | HR checks the assigned shift, policy, and reason if the popup seems wrong. A later punch may need HR approval and a provisional half-day can appear until then. |
| **Provisional half-day / Late arrival pending** | The punch was accepted, but its late arrival exceeded the company allowance or its policy requires approval. This does not change the GPS time. | Complete the normal punch-out and check **Punches** for the decision. Do not punch again to replace the original. | HR/Super Admin reviews the late reason in **Attendance review**, then approves or rejects with a reason. Approval restores the day code; payroll consequences require separate policy approval. |
| **Map unavailable** | The optional map service/key/network failed. It is guidance, not attendance proof. | Read the duty card and address; retry map later. A fresh GPS punch can still work if its other checks pass. | Admin/IT checks map configuration, key restrictions and connectivity. Do not change punch decisions because a map failed. |
| **Server busy / Try again with same punch reference** | A simultaneous punch/attendance action or temporary database lock occurred. | Wait, refresh **Punches**, then retry using the existing in-app action rather than creating multiple evidence records. | If repeated, technical support checks concurrent requests and attendance logs; reviewer checks whether one punch was accepted. |

## If the error is not listed

For a temporary network or **server error**, check your connection, wait briefly and retry once. Do not keep submitting the same form or punch if the result is uncertain. A **404/not found** may mean the record belongs to another company or was removed; a **403/forbidden** means your account does not have access. A **409/conflict** usually means the record changed or another request already completed; refresh and inspect the latest state. A **500/503** that continues needs Admin/IT investigation. Do not attempt database changes or browser-data deletion to “fix” these errors.

When contacting HR/Admin, provide: portal and page, selected company, employee/client code, site, local duty date and time, exact visible message, and what you tried. For an uncertain punch, provide the event reference from **Details for supervisor** if shown. Admin/IT should use that reference and server audit logs to check the result before asking for another punch. Send any sensitive documents only through the approved HRMS flow.
